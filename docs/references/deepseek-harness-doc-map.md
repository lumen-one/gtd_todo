# deepseek-harness 文档地图：每个文件夹装什么

这份是**按目录查的导览**，配合 `deepseek-harness-doc-management.md`（讲规则为什么这么定）读。那份讲原理，这份讲位置。

## 0. 先记住一个前提

这个仓库的文档不是按"重要性"分层，是**按读者的问题**分层。同一件事——"它是什么"、"为什么这么做"、"怎么改它"、"我们被它坑过什么"——四个答案住在四个不同文件夹里。

所以找文档的正确姿势不是"翻最全的那份"，是**先确认自己想知道哪一类**。搞错类别，你会在一份只写现状的文档里找理由，然后得出"这项目没写清楚"的结论。

全景如下：

```
deepseek-harness/
├── AGENTS.md              常驻规则（唯一入口）
├── README / CONTRIBUTING / SAFETY / BENCHMARK / BRAND / NOTICES   对外门面
├── docs/
│   ├── AGENTS.md          文档标准本身（元规则）
│   ├── architecture.md    有顺序的地图
│   ├── subsystems/        65 页，一个子系统一页
│   ├── cookbook/          12 篇，步骤型 how-to
│   ├── cordis-tutorial/   7 章教程 + index
│   ├── cordis-api/        6 页，全生成
│   ├── defensive-patterns/ 5 页领域规则 + README
│   ├── postmortem/        4 篇事故复盘
│   ├── persistence-changes/ 15 条格式变更
│   ├── upgrade-guide/     4 个版本 / 40 篇升级说明
│   ├── i18n/              5 份双语规范
│   ├── user/              产品面向文档（发布到网站）
│   └── 22 个顶层散件      参考型，见 §4
├── .agents/
│   ├── notes/             43 提案 / 286 生效 / 8 否决 / 924 冻结
│   └── skills/            19 个可复用工作流
└── packages/              392 个 README（紧贴代码的契约）
```

## 1. 根目录：只做路牌，不做内容

11 个文件，分三类：

| 文件 | 装什么 | 一句话 |
|---|---|---|
| `AGENTS.md` | 常驻规则十几条，每条 1–3 行 + 理由链接 | 唯一入口，≤2080 词 |
| `CLAUDE.md` | 全文只有一行：`AGENTS.md` | 给 Claude Code 认路，不另写一套 |
| `README.md` | 项目是什么、能力亮点、怎么跑起来 | 对外第一屏 |
| `CONTRIBUTING.md` | 提 PR 的流程、DCO/CLA、review 期待 | 对外 |
| `SAFETY.md` | 安全边界、漏洞怎么报 | 对外 |
| `BENCHMARK.md` | 性能基线数据 | 对内 |
| `BRAND_GUIDELINES.md` | 品牌名、配色、logo 用法 | 对内 |
| `THIRD_PARTY_NOTICES.md` | 第三方许可清单 | 法务 |

**关键设计**：根目录不放任何"怎么做"。README 里没有安装步骤（在 `development.md`），`AGENTS.md` 里没有架构解释（在 `architecture.md`）。根目录只回答"往哪走"。

那个 `CLAUDE.md` 只有 9 字节，是个很省的技巧：别的 AI 工具只认自己那个文件名，与其维护两份规则，不如让它指向唯一那份。

## 2. `docs/AGENTS.md`：唯一描述"文档本身"的文件

它不写产品，写**文档该长什么样**。核心是那张 Tier 表：

| Tier | 职责 |
|---|---|
| 根 `AGENTS.md` | 常驻规则 |
| 子树 `AGENTS.md`（`packages/`、`docs/`、`.agents/notes/`） | 只管自己子树 |
| `architecture.md` | 有序地图：组成、核心包、循环、seam、扩展点 |
| `subsystems/` | 类型定义 + 语义 + 生成的 Cordis API |
| `Agent Notes` | 决策：为什么、放弃了什么、怎么验证 |
| `defensive-patterns/` | review 时强制执行的规则，按产物分页 |
| `postmortem/` | 事故故事 |
| `persistence-changes/` | 格式变更确认与历史快照 |
| `cookbook/` | 编号步骤 + 每步怎么验证 |
| `user/` | 产品面向指南 |
| 包 README | 每包契约：配置、语义、局限、扩展点 |
| 生成型参考 | 从源码重建，禁止手改 |
| Skills | 可复用工作流 |

这张表的第二列是"职责"，第三列是"**不该放这**"——后者才是真正拦住膨胀的东西。

它自己有两条规矩值得注意：**每段一个物理行**（不手动折行），**字数预算 ≤1430**。也就是说，连"文档标准"本身都被预算和门禁管着，不能靠加规则解决规则问题。

---

## 3. `docs/architecture.md`：一张有顺序的地图

`docs/` 顶层唯一"必须先读"的文件。装的是：系统怎么组成、核心包各管什么、一次 agent turn 的循环、能力 seam 在哪、从哪些点扩展。

它**不装**：类型定义（去 `subsystems/`）、单包细节（去包 README）、决策理由（去 notes）、实现状态标注（一个字都不写）。

顺序是有意义的——它按"读的人需要先知道什么"排，不是按字母排。所以它是有序地图，不是目录索引。≤2400 词。

---

## 4. `docs/` 顶层那 22 个散件：全是参考型

散着放不等于乱放。按功能其实只有四组。

### 4.1 政策与标准（手写，6 个）

| 文件 | 装什么 |
|---|---|
| `testing.md` | 测试分几层、什么算"绿得有意义"、哪条测试该放哪层 |
| `development.md` | 贡献者上手：从零到跑通，再到日常命令 |
| `glossary.md` | 术语的**唯一**定义，每个概念一个标准词，带锚点 |
| `ui-radius.md` | 圆角标准：哪些值合法、组件怎么用 |
| `web-styling.md` | 浏览器端样式归属与组件规则 |
| `rescope.md` | vendor 进来的包怎么重新命名空间、怎么发布 |

### 4.2 对外契约（手写，3 个）

| 文件 | 装什么 |
|---|---|
| `api-gateway.md` | Typert API Gateway：服务怎么声明 unary/stream RPC |
| `deepseek-llm-api-wire-extensions.md` | 自定义 HTTP header 与协议扩展，逐条定义 |
| `cordis-primer.md` | Cordis 的最小必要知识，读完能看懂插件代码 |

### 4.3 版本与状态（手写，2 个）

`session-format-status.md` 是 Session 格式版本与发布状态的**唯一权威**——所以正文其他地方提到格式版本时只能链接过来，不能重述。这是"一份事实一个家"的活标本。

### 4.4 生成型（11 个，禁止手改）

顶部都写着 `<!-- Generated by scripts/xxx.ts - do not edit by hand -->`：

`agent-lifecycle.md`（turn/step 时序）、`tool-execution-pipeline.md`（policy 卡在哪）、`capability-seams.md`（服务与 seam 的关系）、`event-producer-consumer.md`（谁发谁收矩阵）、`graph-atlas.md`（文档图索引）、`module-graph.md`（共享实例依赖）、`tool-catalog.md`（模型可见的每个工具与 schema）、`config-catalog.md`（每个插件的 config 块）、`persistence-catalog.md`（持久化事件）、`experimental-persistence-catalog.md`、`cli-help.md`（完整 CLI help）。

**为什么必须是生成型**：这些表的唯一真相在源码里。手写一份必然漂移，漂移后读者不知道该信哪个。所以规矩是"改源码 → 跑 `pnpm run gen-*` → 提交生成结果"，并且有 freshness 门禁——源码变了没重新生成，CI 直接红。

## 5. `docs/subsystems/`：65 页，一子系统一页

这是全仓最大的手写文档集合。每页固定装：**它是什么 → 它搬什么数据结构 → 语义 → 生成的 Cordis API 区**（这个子系统暴露的 service、event、扩展点）。

目录名就是子系统名：`session.md`、`tools.md`、`sandbox.md`、`compaction.md`、`mcp.md`、`subagent.md`、`workflow.md`、`persistence.md`、`settings.md`、`web-client.md`…… 从 `acp` 到 `worktrees`，基本一个概念一页。

**判据**：这里只放"类型与语义"，不放行为叙述。想知道"这个流程怎么跑"去 `architecture.md`；想知道"这个字段什么意思"来这里。

有两条硬规矩：改了一个被记录的类型，**同一笔改动里必须更新拥有它的那一页**；页里的 `ts type-equiv` 代码块要能编译（`doc-typecheck` 管），并且登记进 manifest，防止粘贴的类型和源码脱节。

## 6. `.agents/notes/`：唯一存"为什么"的地方

这是整个体系的重心，也是唯一按**生命周期**组织的目录。

```
.agents/notes/
├── README.md + AGENTS.md        规则：什么时候写、怎么写、怎么死
├── proposed/    43  提案中（未来时）
├── implemented/ 286 已生效（现在时）
├── rejected/    8   想过但否了
└── archived/    924 冻结
```

`implemented/` 下面再按**改动性质**分六类：`architecture` 175、`feature` 36、`process` 32、`testing` 18、`simplification` 13、`bug-fix` 11。

每张卡片固定四面：**问题 → 决定 → 备选与为什么输 → 代价**。

`proposed/` 和 `implemented/` 的骨架**不一样**：提案用未来时、允许写验收标准；生效的禁止出现 `## Proposal` 和 `## Acceptance criteria`，因为已经出货了，再写"计划做什么"就是自欺。状态靠搬目录表达，目录和文件里 `Status:` 行交叉校验。

`rejected/` 只有 8 张，但它可能是最省时间的目录——它记录"这条路试过，输在哪"，防止每隔半年有人重新提一次。

`archived/` 有 924 张，冻结：内容一字不改，SHA-256 记进 `manifest.json`，`.rgignore` 把整个目录排出默认搜索。所以它查得到，但不会被误当成现状。

**判据**：机械改动、局部 UI 调整不用写卡片；新能力、性能改动、实质性行为决定、局部 bug 修复（除非小到纯机械）要写。

## 7. `docs/defensive-patterns/`：把 review 经验变成可执行规则

6 个文件：`general.md`（跨领域的 bug 类）+ 5 个按产物分的页面：

| 文件 | 管什么 |
|---|---|
| `package-surface.md` | 包的导出面、API 边界 |
| `client-components.md` | 前端组件 |
| `conversation-and-session.md` | 会话状态与消息 |
| `remote-and-api.md` | 远程调用、API 层 |
| `general.md` | 通用缺陷类型 |

每条格式固定：**规则（必须成立什么）→ 它防的是什么缺陷 → review 时怎么判**。

差别在于它**不是建议，是 review 会拒的**。所以这一层是"踩过的坑"的沉淀，但已经脱离了故事形态——故事去 `postmortem/`，这里只留判定条件。

---

## 8. `docs/postmortem/`：全仓唯一允许写故事的地方

4 篇，编号 `0001`–`0004`：

- `0001-acp-default-export-drops-inject.md`
- `0002-js-expression-disabled-filesystem-tools.md`
- `0003-web-agent-gui-feedback-loop.md`
- `0004-landlock-partial-notice-misclassified-child-failures.md`

装的是：事故怎么发生、时间线、**为什么我们的流程放它过去了**。README 里明确写了它**不是**什么——不是 bug 报告、不是修复说明、不是 blame。

编号而不是日期，是因为事故要按引用顺序被别的文档提到（"见 postmortem 0003"），日期会漂，编号不会。

---

## 9. `docs/persistence-changes/`：数据格式的账本

15 条 `2026-09-11-initial.md` 这种命名，加一份 README。每条记一次持久化格式的变更：改了什么、旧数据怎么兼容、要不要迁移。

配套还有 `historical-formats/`（完整的历史 schema 快照）。这样做的好处是：读代码只能看到**当前**格式，读这里能看到**它演化过几次、每次为什么**。

判据很严：纯行为变更不进这里，只记**类型/格式**变更。

---

## 10. `docs/upgrade-guide/`：按版本 × 主题分目录

4 个版本目录（`v0.1.7-rc.2`、`v0.2.0-rc.2`、`v0.2.1-alpha.1`、`v0.2.1-alpha.2`），共 40 篇 `guide.md`。

路径长这样：`docs/upgrade-guide/v0.2.0-rc.2/schedule-bundle-retired/guide.md`——**版本 / 这次破坏性变更的主题 / guide**。一个变更一个目录，不合并成"v0.2.0 升级说明"。

好处很直接：用户搜报错信息里的包名，能直达那一篇；而不是在一份三千行的 release note 里翻。

## 11. `docs/cookbook/`：步骤型，每步可验证

12 篇，几乎全是 `adding-a-*`：

`adding-a-package` / `adding-a-tool` / `adding-an-llm-adapter` / `adding-a-remote-api` / `adding-a-session-format-version` / `adding-a-settings-card` / `adding-a-plugin-preview` / `adding-a-vendored-package`，加 `extension-cookbook`（插件形态参考）、`maintaining-dsh-code-review`、`reviewing-persistence-type-changes`、`responding-to-pr-review-on-a-stack`。

判据：**步骤 + 每步怎么验证**。设计理由不写在这里，每篇链到它对应的那张 Agent Note。

这也是为什么它跟 `subsystems/` 不重复：那边答"它是什么"，这边答"我要加一个，按什么顺序动"。

## 12. `docs/cordis-tutorial/` 与 `docs/cordis-api/`：教程与生成参考分开

`cordis-tutorial/` 是**唯一带编号顺序的教程**：`01-first-plugin` → `02-lifecycle-and-effects` → `03-services` → `04-events` → `05-config` → `06-composition-and-hmr` → `07-into-the-harness` + `index`。每章只引入下一步需要的东西。

`cordis-api/` 是 6 页全生成参考：`context`、`events`、`fiber`、`registry`、`service`、`inherited`。

**这两个目录放一起看最有教学意义**：同一批知识，教学路径和查阅路径必须是两份文件。想合成一份的结果是——教程里塞满查表，查表里塞满循序渐进。

---

## 13. `docs/i18n/`：双语契约，5 份规范

`README.md`（配对契约）+ `translation-rules.md`（怎么翻）+ `terminology.md`（术语对照，唯一权威）+ `style-samples.md`（好坏样例）+ `translation-prompt.md`（喂给模型的提示词）。

机制是 `.md` + `.zh.md` + `.i18n.yaml` 三件套，yaml 按**章节**记哈希对，两边物理行数必须完全相等。改英文不改中文，`verify-translation-pairing` 直接红；`--write <pair>` 是人工确认"我认可这处变更"的动作。

**单语项目别抄这套**，成本翻倍。但它的思路可以借：**"这一节有没有变过"应该是机器能答的问题**。

---

## 14. `docs/user/`：产品面向，不是贡献者面向

`docs/user/` 下按 `guide/`、`develop/basic`、`develop/framework` 组织，每篇也是双语三件套。内容是给**用这个产品的人**看的：怎么配、怎么发布、怎么写第一个插件。

**它和 `docs/` 其余部分的分界线是读者身份**：`development.md` 是"你要改这个仓"，`user/` 是"你要用它"。混在一起的后果是贡献者文档里塞满入门教程，或反过来。

这个目录由文档网站投影消费，所以格式受 `project-doc-site` 约束。

`dsh-doc`（文档怎么写、放哪、怎么验）、`dsh-translate-docs`（双语翻译）、`dsh-prose-standard`（文风与覆盖度）、`dsh-code-review`、`dsh-archive-agent-notes`、`dsh-create-upgrade-guide`、`dsh-find-simplifications`、`dsh-pre-push-checks`、`dsh-error-handling`、`dsh-client-ui-ux`、`dsh-responsive-ui`、`dsh-ci-test-reliability`、`dsh-merging-stacked-prs`、`dsh-speed-up-perf`、`dsh-trim-cot-leakage`、`agent-experience`、`cordis-styling-nitpicking`、`dsh-official-plugin-artwork`、`record-browser-gif`。

`dsh-doc` 内部只有 1 个 `SKILL.md` + 5 份参考 + 模板：

| 文件 | 管什么 |
|---|---|
| `structure-hierarchy.md` | 分层与归属判据 |
| `style.md` | 排版与文风 |
| `metadata-links-i18n.md` | frontmatter、链接、双语元数据 |
| `review.md` | 文档 review 怎么过 |
| `website-sync.md` | 网站投影同步 |

**Skills 和 docs 的边界**：skills 放"怎么做"（工作流、判定标准），docs 放"是什么"（产品与运行时契约）。所以同一个主题会在两边各出现一次，但内容不重叠。

## 16. `packages/`：392 个 README，紧贴代码

每包一份，固定装：**这个包干什么 → 怎么配 → 语义 → 局限 → 扩展点**。有的还有 "Model Experience" 一节（模型实际会看到什么）。

这是全仓最细的一层，也是唯一"改了代码基本必须同笔改"的文档层。判据：**它只写自己这个包的契约**。JSDoc 里已经有的不复述，生成型 catalog 里有的不复述，别的包的事不管。

392 这个数字说明一件事：**文档可以碎，但不可以没有归属**。每个包都有主，就没有"这份文档没人管"的角落。

## 18. 五条能立刻用的判断

1. **找不到文档时，先问"我要的是哪一类答案"**，而不是搜关键词。四类答案四个家。
2. **正文里出现"这次改成了""已实现""计划中"，就是错位**——历史归 commit 和 notes，状态归代码。
3. **一句话在两处出现，第二处必须改成链接**。重复不是风格问题，是"改一处漏一处"的定时炸弹。
4. **生成型文件（11 个）永远改源码**，别改 md。
5. **想加新文档前，先确认现有哪一层的题目能容纳它**。容不下再新建，新建就要在 `docs/AGENTS.md` 的 Tier 表里给它一个位置——否则它会变成没人管的孤儿。
