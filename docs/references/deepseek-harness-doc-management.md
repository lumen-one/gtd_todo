# deepseek-harness 文档管理策略研读笔记

> 外部项目参考，**不是本项目现行口径**。本项目正文仍只有 README + architecture.md + ui-interaction.md 三份。
> 研读对象：`C:\Users\zzz\Desktop\workspace\deep harness\deepseek-harness`（读于 2026-10-21）。

## 一、这套体系在解决什么

不是"把文档写好看"，而是三个更硬的问题：

1. **事实重复**——同一句话散落在 README、架构文档、注释里，改一处漏三处，最后没人知道哪份是真的。
2. **决策失忆**——代码能告诉你"是什么"，但"当时为什么不那样做"只有人能记，人一走就重新争论一遍。
3. **文档腐烂**——昨天的"已完成/计划中"今天就是假话；没有机器的强制，规矩活不过三个月。

它的答案分别是：**一份事实一个家**、**决策走路径编码的状态机**、**写作规则全部落成可执行门禁**。

规模感（说明这套东西为什么值得这么重）：`docs/` 239 篇英文 + 234 篇中文 + 234 份配对记录；`.agents/notes/` 共 1262 篇（其中 924 篇已冻结归档，约 337 篇活跃：implemented 286 / proposed 43 / rejected 8）；`packages/` 下 389 个 README，全部双语配对；文档类门禁 43 项。

## 二、全景：文档按"职责"切层，不按格式切

这是整套体系的骨架（`docs/AGENTS.md` 的 tier taxonomy 表）。每一层只干一件事，且有明确的"不该写在这里"：

| 层 | 唯一职责 | 明确不属于它 |
|---|---|---|
| 根 `AGENTS.md` | 常驻军规：每次会话都要在上下文里的规则，每条 1–3 行 + 链接 | 故事、完整示例、情景化流程、任何从别处复述的内容 |
| 子树 `AGENTS.md` | 只对该子树生效的规则 | 根文件已承载的全仓规则 |
| `architecture.md` | **有顺序的地图**：组成、核心包、循环、接缝、扩展点 | 类型定义、单包细节、决策理由、实现状态标注 |
| `subsystems/` | 每个子系统一页参考：类型定义、语义、生成的 API | 行为叙事 |
| `Agent Notes` | **决策记录**：为什么、放弃了什么、要求什么验证 | 迁移计划、验收清单、已实现后还说"应该…" |
| `defensive-patterns/` | 评审时强制执行的反模式，按产物分页 | 类型语义、决策理由 |
| `postmortem/` | 事故叙事——**唯一允许写"故事"的层** | — |
| `cookbook/` | 带编号验证步骤的操作指南 | 设计理由 |
| 包 README | 单包契约：配置、语义、局限、扩展点，**紧贴代码** | 复述 JSDoc、手抄生成的目录、别的包的事 |
| 生成型参考 | 从源码机械再生的穷举表（工具目录、配置目录、模块图、CLI help） | 任何手改 |
| Skills | 可复用的工作流与判断标准 | 产品契约 |

配套的一条判据比表本身更重要：

> **一个文档的主题 + 它在树上的位置，共同决定它的 scope。** 只把自己的主题讲到恰当深度，直属子级只讲目的、责任和高层行为，更细的东西链接到拥有它的后代。文档类型（教程/参考）不会拓宽这个 scope。

还有一条放置口诀：bug → postmortem；理由 → Agent Note；步骤 → cookbook；类型 → subsystems；包契约 → README；常驻规则 → 根 AGENTS.md + 一条理由链接；评审强制规则 → defensive-patterns。

## 三、Agent Notes：把"决策"做成路径状态机

整套体系里最值得抄的一块。它用**文件路径**同时编码三个维度：

```
.agents/notes/{lifecycle}/{class}/yyyy-mm-dd-topic-title.md
                ↓          ↓
          proposed/     feature      （新增用户/模型可见能力）
          implemented/  bug-fix      （修缺陷或补 postmortem 暴露的洞）
          rejected/     simplification（删代码/行为/面无新增能力）
          archived/     architecture （关于出货源码的结构决策）
                        process      （围绕代码的工具/政策/流程）
                        testing      （测试基建与策略）
```

几条硬机制：

- **生命周期是搬到另一个目录**，不是打标签。文件动，`Status:` 行跟着改，门禁交叉校验两者一致——目录说 proposed、正文写 implemented，直接红。
- **每个生命周期一套固定骨架**，门禁拒绝串味：
  - `proposed/`：Problem → Proposal → 自定义 → Alternatives considered → **Acceptance criteria** → **Risks**
  - `implemented/`：Problem → Decision（**现在时，描述已出货现实**）→ 自定义 → Alternatives considered → Consequences。`## Proposal`、`## Plan`、`## Acceptance criteria` 在 implemented 里是被禁的——那是"规格腔"。
  - `rejected/`：提案原样冻结，判决写在 `Status: rejected — 一句话为什么` 那一行。
- **`## Alternatives considered` 是强制的**。理由写得极准："一个只记录了决定的记录，会邀请别人重新打一遍这场仗——而这正是 Agent Notes 存在的意义所在。"没记录备选（而不是编造）的老笔记允许一条 grandfather 注释，超出日期就必须补。
- **implemented 笔记要跟着代码改**：改名、换路径、改默认值，同一次改动里就地改事实；但**不许把决定本身改掉**——要翻案就新写一篇并互相链接。
- **归档是永久冻结**：`archived/{class}/…`，插入一行 `Archived: YYYY-MM-DD`，然后整组（英文 + 中文 + 配对记录）按 SHA-256 追加进 `manifest.json`，只增不改。`--write` 模式先证明已有封印全部未变，再追加新的。CI 要用可信 base SHA + 完整历史，否则浅克隆会导致基线缺失。`.rgignore` 把归档排出默认搜索——免得 924 篇陈旧事实按字面匹配压过现行文档。
- **刻意不建 `INDEX.md`**：路径已经编码了生命周期、类别、日期，中央索引等于把元数据抄一份，还让所有无关笔记的改动挤在一个生成文件里冲突。

这篇论文级的规则本身也是 Agent Note 写的（`implemented/process/2026-07-26-frozen-agent-note-archive.md`），连"为什么不直接删"都有备选分析。**规则自己遵守自己的格式**，这是它可信的原因。

## 四、双语：三件套 + 章节哈希（机制比语言更值得学）

它的双语不是"顺便翻一下"，而是一份带确认动作的契约：

- **一对 = 三个同级文件**：`foo.md`、`foo.zh.md`、`foo.i18n.yaml`。没有 `zh/` 目录、没有独立翻译仓、没有中英混排。**不成对不能合入。**
- **两边同等权威**：可以先写中文再译英文，不存在"英文为准"。
- **配对记录按章节存哈希对**：key 是英文标题的 slug 路径（`/foo/usage`），值是两侧该节内容的哈希。改不同章节 → 改不同行 → Git 默认文本合并就能合上；只有两边同时改同一节才冲突。代码块和生成区域不进哈希（这两类本来就被要求两侧逐字节相同）。
- **`--write <pair>` 必须点名**：重记哈希 = "我确认这对是一致的"，是留给评审看的动作。`--write --all` 存在，但是显式的全仓形式。
- **结构签名一比一**：标题层级与顺序、列表种类、有序列表起始号、列表项数、表格行列数、链接目标（含 query/fragment）、代码块逐字节。以及**物理行数完全相等**——中文在对应那一行里自由翻译，不硬折行。
- 门禁自己承认局限，这句值得抄："**门禁为绿，只意味着这对在被确认的这一刻内容一致，不意味着这次确认靠得住。** 它查哈希和结构，判断不了两边说的是不是同一件事。"

## 五、门禁：规则不落成代码，就等于没有规则

- **字数预算**：`scripts/doc-budgets.manifest.json` 给常驻文档定上限——根 `AGENTS.md` 2080 词、`docs/AGENTS.md` 1430、`architecture.md` 2410、`packages/README.md` 994、`cordis-primer.md` 600、`testing.md` 1350、`packages/AGENTS.md` 810。超了按固定顺序处理：**迁移**（本来属于别层）→ **压缩**（属于这里但能更短）→ **抬高上限**（真的需要这些字数，且要在 PR 里为清单 diff 辩护）。另外两条很关键：
  - "上限是护栏，不是削减目标"；达标时保留至少 5% 余量；超了就先冻结上限，等迁走或压缩后再降回来。
  - 包 README 的英文 Summary 单独卡 100 词。
- **两档速度**：`pnpm run test:docs` 跑 21 项快速检查（配对、折行、链接、README 门禁、预算、技能元数据、笔记格式），不建构建树、不重算生成器、不建站；`pnpm run doc-sync` 跑全量 43 项。日常用快档，PR 用全量——**"本地绿不替代 PR 级的全量绿"**。
- **pre-commit 只卡最便宜的两条**：暂存区的 `*.i18n.yaml` 验配对、归档笔记验封印。其余交给 CI，钩子保持秒级。
- **门禁有自测**：`scripts/doc-standard.spec.ts` 检查"参考示例仍然合法、kind 与模板一一对应、技能里没有抄错的过时值"。**标准本身被测**，否则标准会先烂。
- **每条承诺都要有反例**：验证规则时同时要求一个合法 fixture 和一个非法 fixture，证明门禁真的会红。

具体检查项举例（都能一句话说清）：折行（段落必须是单物理行）、死链、根相对路径引用、生成物新鲜度、类型粘贴等价（`ts type-equiv`）、导出 JSDoc、Mermaid 语法、术语黑名单（`provenance` 这类模糊来源标签被禁）、站点片段、升级指南存在性。

## 六、写作纪律：八条，每条都在防一种具体的病

1. **只写现状**。历史归 commit / PR / Agent Note / postmortem。正文里的机制用**活的名字**，不写"第 3 阶段""新方案"这种位置描述。
2. **一段一物理行**（`verify-md-wrap` 强制）。靠编辑器软折行。好处很实在：diff 精确到段，改一句话不会整段重排，评审能看见真改动——这对"逐行契约"和"通读抓矛盾"的工作方式几乎必需。
3. **slop 清单**，六种病各有名字：重复规则（搜一个特征短语，只留一处）、历史出现在不该出现的层、正文里写"已实现！/未来：…"（状态会腐烂，布局和清单已经承载了它）、手抄目录/JSDoc/测试清单、**推理转录**（分步实现叙述、显然分支的证明、测试走查、被否掉的局部方案——留下结论，删掉推导路径）、段落墙、强调通胀（处处加粗等于没有重点）。
4. **术语纪律**：一个概念一个词，不为了变化换同义词；`seam` 只留给定义过的 capability seam；不用隐喻式的 "gate"/"vocabulary"/"surface" 去代替具体的检查、类型、API、行为。甚至专门有一条：写 `contract`/`boundary`/`shape` 前先问有没有更准确的说法（`response fields`、`JSON validation`、`ESM exports`），`contract` 只留给前置/后置/不变量/兼容承诺。
5. **受控技术英语**（ASD-STE100 启发，非认证）：句子有明确施动者、一句一个指令、三个以上条件改用列表、不删 `must`/`may`/`never` 与时间、例外、数字来凑长度。20 词（指令）/25 词（描述）是**评审提示，不是门禁**。
6. **事实核查 = 跑一遍**。每条命令、默认值、错误码、平台差异，必须在当前 checkout 上实跑；跑不出来就删掉，不许"从相邻包的 README 类推"。改旧页面前先 `git fetch origin` 对比 master——**master 上的陈述过时了，它依然是错的**，要照代码改，不是照旧文改。
7. **Dev Note 是唯一的"草稿区"**。每页最后可以有 `## Dev Note`，明确标注"非权威"，放没想清的方向、量到的数据、进度指针；工作结束要把耐久结论提升到正式层，把可复用理由搬进 Agent Note，删掉闲聊。空的就写 `None.`，不许放占位废话。
8. **可读性靠版式而非修饰**：开头 `## Summary` 三到五句讲"读者能做什么、为什么在意、主运行模型、最重要的边界"；`-----` 分隔主要部分；重型开发者细节与 Dev Note 用 `<details>` 折叠但**标题和锚点可见**；加粗只给改变行为的那个从句。

## 七、生成型内容与网站：只允许单向派生

- 穷举型参考（工具目录、配置目录、模块图、CLI help、Cordis API）**由源码再生**，门禁查新鲜度和配对。生成区域同时写进中英两页，所以再生进不需要人工重译。
- 网站是**投影**不是第二份拷贝：`website/docs.ts` 是显式白名单，`project-doc-site.ts` 把它们重写成一次性的 `website/.generated/`，VitePress 再构建。规则三条：只在规范源里编辑；新增页面加一条清单项；移动/删除要源、清单、入链原子一起改；**永不编辑 `.generated/`**。
- 一条延伸判断：发布站 ≠ 同步进构建。"同步内容进构建不等于发布，部署是独立的、需要显式请求的一步。"

## 八、它明确禁止的事（比正面规则更好记）

- 不许把规则在两层各写一遍（只留一个家 + 链接）。
- 不许在正文里写实现状态（"已实现"会变成谎话）。
- 不许手抄源码能给出的目录、清单、JSDoc。
- 不许在文档里保留推理过程。
- 不许在 implemented 笔记里写"应该/计划/验收标准"。
- 不许编辑已归档笔记（连修断链都不行，除了一条登记在案的例外）。
- 不许给归档笔记配中文（冻结即冻结）。
- 不许建中央索引文件。
- 不许只手改生成物。
- 不许用隐喻代替具体名词。

## 九、搬到 gtd_todo：该抄什么，别抄什么

先说结论：**抄三条机制，不抄它的规模。** 它有 389 个包、300+ 贡献者级的分工需求撑着 1262 篇笔记；照搬到单人 + 一个 agent 的 Flutter 项目上，维护成本会直接压垮收益。

### 建议抄（按性价比排序）

**1. 恢复"为什么"这一层，但只为会被重新质疑的取舍建记录。**

现在 `architecture.md` / `ui-interaction.md` 只保留结论——删 changelog / crosswalk / D1–D19 / 47 条决议是对的（那些是流水账）。但代价是"当时为什么不那样做"只剩下 git 历史。有几条口径明显属于"未来一定会有人（包括未来的你）想推翻"的类型，值得各留一张小卡片：

- 锚点跨重锚沿用（不做会被无关任务推后提醒）
- 排序四档（infeasible 与 normal 不同池）
- interval 两段对数放缓（硬顶会让远期任务天天响）
- 无排序档 = 标准档的弱化版，而不是"把有截止的都搬进今天"
- snooze 到期定时触点（标准档下走不到 `_reload`）

做法：新建 `docs/decisions/`，一决定一文件，命名 `yyyy-mm-dd-topic.md`，骨架就四面——`## 问题` / `## 决定（现在时）` / `## 备选与为什么输` / `## 代价`。**不建索引**（文件名就是索引），不建状态目录（做了就在，没做不要写"计划中"）。宁可只有 5 篇真的，也不要 40 篇凑数。

**2. 一段一物理行。**

现在两 docs 是 CRLF 且按自然段硬折行。改成"段落 = 一行"后：diff 精确到段、改一句不重排整段、评审看得见真改动、和"逐行契约"的读法天然契合。成本是一次性重排（会有一个巨大的 format-only commit，值得单独一笔），之后几乎零成本。

**3. 给两份正文加字数上限。**

它证明了一条：**"写短点"从来不管用，"超了必须三选一"才管用**。给 `architecture.md` 和 `ui-interaction.md` 各定一个当前词数 +5% 的上限，写进一个 10 行的检查脚本（`dart run tool/check_docs.dart`）：超了只有三条路——迁到别层、压缩、或在 diff 里说明为什么必须加。这比任何文档规范条款都有效，因为它在你写字的那一刻就生效。

配套两条低成本检查可以塞进同一个脚本：**死链**、**段落内换行**。三条加起来不到 100 行 Dart。

### 建议不抄

| 它的机制 | 为什么不适用 |
|---|---|
| 双语三件套 + 章节哈希 | 单语项目，成本直接翻倍；哈希确认的价值要"多人并行改同一文档"才成立 |
| `kind` 系统 + 8 套模板 | 你只有三类文档（架构口径、交互决议、README），模板化会变成填表 |
| SHA-256 冻结归档 | 你刚刚才选择删掉历史记录、把结论内联；再造一个 900 篇的冻结仓是反向操作 |
| 43 道门禁 / 生成型目录 / 网站投影 | 没有 389 个包、没有站点。生成器是为"人手一定会抄错"的规模准备的 |
| 子树的 `AGENTS.md` 分层 | 项目只有两份正文，分层会立刻产生"这条规则该写哪"的内耗 |

### 一条元教训

它整套体系最狠的地方不是哪条规则，而是：**每条规则都有一个可执行的门禁，每条门禁都有一个反例证明它会红，而且门禁自己也被测试。** 规则一旦只写在文档里，它的半衰期大约是三个月。所以上面第 3 条（可执行的上限）优先于第 1 条（决策卡片）——先有量尺，再谈口径。
