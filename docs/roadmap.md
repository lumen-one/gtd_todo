# 未来方向

> 这里全是**候选**：不是承诺、没有排期、不能当契约引用。
> 契约在 `architecture.md` / `ui-interaction.md`，理由在 `decisions/`，这里只有"可能往哪走"。

## 这份文档怎么用

三条边界，照做就不会把它变成第二份正文：

1. **只写"想做什么 + 什么条件下做"**，不写日期、不写"预计""尽快"。写下条件就够了，
   条件到了自然会想起来。
2. **真开始做的时候**：先在 `decisions/` 落一张卡片（为什么选这条路、否了哪条），
   再改正文契约，**然后把这里对应的条目删掉**。留在两处就是两份计划。
3. **决定不做的时候**：删掉条目，理由进 `decisions/`。没有理由的删除，半年后会被重新提出来。

## 二、等触发条件

来源是 `architecture.md` §11 每条局限的"触发重新评估的时机"。**触发条件不成立就不动**——
这些改动大多要同时动 repository / codec / 组装点，没有真实案例就是给自己找活。

### 2.1 等真实案例（防御性，出了才改）

| 方向 | 触发条件 | 要动哪几层 |
|---|---|---|
| 单写入者 / 实例锁 | 双开或两引擎并发真的丢了一次写 | 组装点 + 文件锁或常驻进程 |
| 行内稳定 id（`^task-001`） | 出现在 Obsidian 改名 + 增删行导致的错配案例 | 人类文档格式 + 配对降级链 |
| 长期任务补 `digest` | 出现改名后"多出一条、旧条目还在"的真实案例 | sidecar 编码 + 配对 |
| 同步的时间戳向量 | 两台从机同轮推同一文件真的打起来 | `LanSyncAdapter` 方向裁决 |
| "未落盘"提示 | 出现"看着改好了、重启回退"的反馈 | `TaskService.persistFailures` 接进设置页 |
| 手势排除区扩到整条边 | 用户抱怨"贴边滚清单误触返回" | 原生 overlay 声明 + 放弃"边缘=返回" |
| 标准模式改动清单构成 | 明确要求"没开提醒的都不进今日" | `buildTodayView` + 今日清单页 |

### 2.2 等规模上来（容量问题，不是设计问题）

| 方向 | 触发条件 | 做法 |
|---|---|---|
| `tasks.md` 按分类分文件 | 单文档超过数千行 | 改 codec 的读写单位，人类文档侧仍是纯 Markdown |
| 目录加项目/层级 | 任务量或组织需求真的上来 | 同时动 repository / codec / 组装点，是一次大改 |
| 周期实例归档子目录 | `.gtd/` 文件数膨胀到影响浏览 | 归档目录 + 打开时按需生成 |

### 2.3 功能缺口（想做，缺的是时间不是决策）

| 方向 | 现状 | 落点 |
|---|---|---|
| **AI L2** | 契约侧只留 C1/C3 两条约束；分级授权与提案流程的草案在本文附录 | 新增 `AiProvider` 实现 + 命令通道的白名单校验 |
| 每年重复的节假日 | `holidays` 只支持具体日期 | `WorkTimeRule` 加周期规则 |

### 2.4 交互补完（都是已知的洞，代价明确）

| 方向 | 现在的样子 | 补上要付什么 |
|---|---|---|
| 新任务插到手动序中间 | `manual_order` 只覆盖被拖过的段，新任务从末尾开始 | 加一个"插到某件之前"的入口，本质仍是写序号 |
| 固定时点组 / 例行组可拖 | 时刻就是序，实例每天新生没有可持久序号 | 要先回答"拖了之后明天怎么办" |
| 桌面窄窗口折叠侧边栏 | 窄于 720 退回单栏，再窄就吃留白 | 做折叠栏或面板抽屉化 |
| 桌面鼠标按住横拖翻页 | Flutter 默认不接 mouse 拖动 | 桌面壳包一层放开 mouse 的 `ScrollBehavior`，注意别连带影响列表纵向滚动 |
| 桌面设置页整块重做 | 右栏沿用同一份 `SettingsPanel`，只按能力表裁项；『关于』因此也没摆上桌面 | 需求还没定形；动手前先落一张卡片，再把能力表里那项摘掉 |

## 三、架构上留好插座、还没接的

`architecture.md` §0 那句"换件不伤车"不是修辞，下面这些换上去不用动核心：

- **SQLite 存储**：实现 `TaskRepository` / `TaskCodec` 即可，`main.dart` 换一行注入；
- **EDF / 其他调度算法**：实现 `Scheduler`，注册进算法注册表；
- **别的 LLM**：实现 `AiProvider`；
- **新平台 shell**（iOS 等）：架构支持，缺的是那一份平台适配器与需求。

这些之所以没做，**不是因为难，是因为没有需求**。插座空着不影响车跑。

## 附录：AI 接口设计草案

> 分级授权、类型定义与提案流程的设计草案——**不进契约**。契约侧只剩两条仍生效的
> 约束（写路径唯一 C1、无第二条写路径 C3），见 [架构文档](architecture.md) §6。
> **开始实现时**：先落一张 `decisions/` 卡片，把本节改成 `architecture.md` §6 的契约，
> 然后删掉本节。

四级权限，默认只开 L0/L1：

| 等级      | 能力                       | 机制                                                              |
| --------- | -------------------------- | ----------------------------------------------------------------- |
| L0 读     | 看任务、调度结果、参数     | `SystemSnapshot`（只读投影）                                      |
| L1 提案   | 估工时、拆任务、建议改截止 | 产出 `Proposal`，进 UI 待确认列表，**人确认后才执行**             |
| L2 软控制 | 微调调度参数               | 只许改 `params` 声明范围内的值；记事件（origin=ai）；可见、可拒绝 |
| L3 硬控制 | 换算法、改规则             | 默认锁死，永不自动执行                                            |

类型定义：

```dart
abstract class AiProvider {
  String get id;
  /// 每个快照返回的提案数不得超过 proposalCap（上限值未定，
  /// 接口按此约束实现方）。
  Future<List<Proposal>> propose(SystemSnapshot snapshot);
}

/// Command = 一次参数化的 UserAction（architecture.md §3.2 规则 C1 的命令封装）。
/// CommandKind 与 payload 字段未定，落地 AI 前补全。
class Command { final CommandKind kind; final String taskId; final Map<String, Object?> payload; }

class Proposal {
  ProposalKind kind;        // estimate / decompose / retune / suggestDeadline
  String rationale;         // 给人看的理由
  List<Command> commands;
  ProposalStatus status;    // pending / approved / rejected / expired
}

class SystemSnapshot {
  final List<TaskView> tasks;          // 只读投影，非可变 Task
  final ScheduleResult schedule;
  final String activeSchedulerId;
  final Map<String, num> schedulerParams;
  final DateTime generatedAt;
}
// 裁剪规则：不含正文 description 全文与 metadata 自由字段，
// 除非 Provider 声明需要并在快照请求中显式开启。TaskView 字段清单未定

/// 提案确认入口（与人类点击共用同一命令通道）：
/// TaskService.applyCommands(List<Command>, {required EventOrigin origin})
```
