# 口径联动表（crosswalk）

> **这是什么**：同一产品口径会在两份文档里各落五六处（正文条款、名词表、决议表、
> 决策记录、局限表、附录登记表）。本表回答一个问题——**改动某个口径时，除了正在改的
> 那一处，还必须同步扫哪些小节**。
>
> **什么时候用**：改任何口径之前看对应那一行；改完照着扫一遍。全程约十秒。
>
> **为什么需要它**：2026-10-13 的教训——v0.12 修订把"无排序"从"放开锚点准入"收窄为
> "成员不变、只不排序"，§6.1 / §7.0 / §19 / 决议 43 / arch 一侧都改了，唯独漏了
> ui §11"边界与异常"（留着初稿的"清单会变长、切回自动"）。漏的原因不是粗心，是那一节
> 不在"这次要改什么"的清单里，根本想不起来去翻。本表把这份清单从记忆里搬出来。
>
> **和 grep 的分工**：grep 抓"换了说法"的（同一关键词多处出现），抓不到"换了词"的
> （§11 用的旧词是"排序模式/自动"，搜新口径关键词零命中）。本表管"没想到那儿也有
> 一份"，文末的旧词对照管"换了词"，两者互补，都要用。
>
> **冲突裁决**：正文 + 决议表 / D 表为准；发现冲突按"后来的口径赢"处理，顺手把旧条款
> 清干净，并在 changelog 记一笔。

## 二、每次改完口径的收尾检查

1. **对着上表扫一遍**对应行列出的小节，别只扫"记得住的"；
2. **grep 旧词**（文末对照表）——防"换了词"的残留，这是本表和 grep 的分工里 grep 负责的那半；
3. **决议表 / D 表**：被修订的条目加修订注（历史条目不改写，只标注，同 v1.11 对 v1.4 记录的做法）；
4. **changelog 追加一条**：口径变化 + 理由 + 明确不做（代码落点不写，git log 有）；
5. **测试口径同步**：改调度/提醒/存储口径时，对应测试文件（如 `schedule_mode_test.dart`、
   `markdown_task_repository_test.dart`）的断言按新口径过一遍——2026-10-13 那次就是测试
   按新口径重写了，但 analyze/test 因工具链故障未跑，状态只能记"待补"。

## 四、维护本表自身

- 两份文档**新增或删并章节时**（如本次 changelog 外移），同步更新本表的小节编号；
- 本表不追求覆盖每一次小修订，只收**口径级**改动（会牵动多处的那种）；
- 发现新的"换了词"残留时，把旧词补进文末对照表——它靠真实漏扫案例生长，不靠想象。
