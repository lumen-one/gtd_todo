### v0.9（2026-10-11）：算法层与提醒模式

本次只动**算法层**（用户要求：先改文档、再改代码；内核与存储形态不动）。
需求口径的三条新增 = 决议 38/39 与 §7.0。

**A. 新增：两种提醒模式（决议 38）**

- 默认**标准模式**：只排列不提醒；单个任务可在编辑表单里开『提醒我』（metadata `remind`）；
- **完整模式** = 原方案（算法判定该响的都响）；
- 设置页『提醒』节新增模式开关（默认标准）；模式落 `settings.json` 的 `reminder_mode`。

**B. 新增：排序算法换成"时间裕度优先"（决议 39）**

- `risk = f(slack)` 取**非线性**指数族（`exp(−(slack/τ)^γ)`），
  `priority = risk × importance`，`importance`（优先级）**缺省 3**；
- 新算法 `slack-priority.v1` 成为**默认**；旧 `slack.v1` 留在注册表里供对照 / 影子运行；
- **界面观感不变**：`risk`/`priority` 都是派生值，**不落盘、不进人类文档**，
  界面也不显示这个排序分（顺序本身就是表达；裕度这类派生量照旧可展示）。

**C. 一处口径必须说清（同名不同物）**

内核属性文档的 `priority` 键**始终**是**人定的优先级**（= `Task.importance`，缺省 3）；
算法算出来的那个叫**调度优先级**（`risk × importance`），只活在内存里。
§1 名词表、§7.1、决议 39 与架构合同 §3.2 B3 / D16 / 附录 B.2 **六处口径一致**。

**D. 明确"模式不改清单"**

分组、编号、顺序、今日清单准入在两种模式下**完全一致**——`nextReminderAt` 作为
**锚点**照常算，门槛只决定它会不会变成"真的响"。所以切模式**不会让条目增减**
（§6.1、§7.0、架构合同 §12 最后一行）。

**E. 验证**

- `flutter analyze` 干净（只剩 3 条既有的 `onReorder` 弃用 info）；**146 个测试全绿**；
- 新增 21 个用例，其中"默认标准模式不产出提醒""给这一件开提醒才响""时点提醒同门槛"
  是本次需求的正向护栏；**既有调度/提醒用例显式改用完整模式**——不改就一个都响不了，
  这本身就是默认值生效的证据；
- 桌面壳在标准模式下把表头文案改成
  "不提醒（标准模式：给任务开『提醒我』，或切完整模式）"，widget 测试两条断言分别覆盖
  标准与完整。

### v0.12（2026-10-12 拍板 / 2026-10-13 修订）：调度模式三档

本次把"**排先后**"和"**出不出声**"合并成**一组三选一**的产品开关：**完整 / 标准（默认）/
无排序**（决议 43）。初稿做成两个并列开关（提醒模式 + 排序模式），并按原稿把"今日可推组
不再按锚点准入"也写进了决议；用户指出三处问题，本版按他的口径全部重写：

1. **无排序跟标准、完整是并列概念**，不是另一个维度 → 三档合一，设置页放在一起；
2. **实现它只该动业务层** → 内核（`Scheduler.schedule`）一行未改；
3. **无排序 = 今天的任务不排序**，不是把所有任务都塞进今天 → 今日可推组的成员三档一致，
   它是"标准模式的再弱化版"。

一句话：**完整 = 排 + 响；标准 = 排 + 不响；无排序 = 不排 + 不响**（§7.0 那张表）。

**A. 三档只在两件事上不同**

| | 今天这几件的先后 | 会不会响 |
|---|---|---|
| 完整 | 算法排 | 算法判定该响的都响 |
| 标准（默认） | 算法排 | 默认不响（单件可开『提醒我』） |
| 无排序 | **人拖（`manual_order`）** | 与标准一致：默认不响 |

除此之外三档**完全相同**：今日清单有哪几件（仍是"锚点落在今天 / 今天到期"）、多久催一次、
逾期与"做不到"的提示、各组内部的排法（逾期置顶 / 固定时点按时刻 / 例行按发生时刻 /
被挑散件在最后）、任务池的整理序——一律不动。

**B. 为什么不改内核**

内核那份排序（`ScheduleResult.items`）不只是给清单看的：它还决定 `nextTask`（下一站是谁）
等计算结果，而且一旦把 `sortMode` 塞进 `Scheduler.schedule` 的签名，每个算法实现
（包括影子里跑的那个对照算法）都得处理一个没有数学的分支。所以这一档**纯粹做在业务层**：
`buildTodayView` 收 `scheduleMode`，无排序时不采用 `items` 的顺序，改用手动序。
副作用是好的：注册表里不会多出一个没有数学的假算法，§14"用户自选算法不做"的口径不变。

**C. 手动序的边界**

- 只作用于**今日可推组**；任务池仍是自己的整理序（`pool_order`），两套序号互不干扰；
- 拖一次整段重编号、`manual_order` 记在任务上、**重启保留**；没排过序的按创建先后沉末尾；
- 无排序档下**没有"插队"这一层**——顺序本身就由人定，不需要给算法排序打补丁；
  `pinned` 标记仍留在任务上，切回标准/完整时照旧生效；
- 切档**不迁移、不改写任何数据**：手动序在标准/完整两档下原样躺在元数据里、只是不生效。

**D. 明确不做（防将来被当遗漏）**

- 无排序 ≠ 不调度：裕度、提醒节奏（多久响一次）、逾期与"做不到"的提示全部照旧，
  把这些一起关掉等于把提醒系统拆了；
- 无排序 ≠ 第三个算法（见 B）；
- 无排序档下的智能整理 / 一键按算法重排：不做（§14）；
- 给固定时点组与例行组排手动序：不做（时刻就是序 / 实例每天新生没有可持久序号）。

**E. 代码已落地，验证状态 = 待验证（工具链跑不起来）**

落点：`ScheduleMode`（含 `reminderMode` / `isManual` 派生）与 `compareManualOrder`、
`Task.manualOrder`、sidecar 与旧 codec 登记 `manual_order`、
`AppSettings.scheduleMode`（`settings.json` 的 `schedule_mode`，仍读得懂旧 `reminder_mode`）、
`TaskService` 的 `scheduleMode` / `updateScheduleMode` / `setManualOrder`、

`onScheduleModeChanged`、设置页『提醒与排序』节三选一、今日面板拖拽在 `isManualSort`
下改走 `setManualOrder`。**回退记录**：内核层（`Scheduler.schedule` 的 `sortMode` 入参、
两个算法与影子调度的分岔）已按"不该改"撤销于一笔 revert。

`flutter analyze` 与全量 `flutter test` **没跑起来**：机器上 Windows 命名管道耗尽
（OS error 231，flutter 工具自己崩），与本版改动无关。前一版（口径未修订时）曾跑出
analyze 干净 + 160 测试全绿，本版**改动面覆盖其中绝大部分断言**（旧的

### v0.14（2026-10-13）：三处交互缺陷修复（翻页 / 笔记路径 / 拖动闪动）

用户实测报的三个问题，都是"写了但用不起来"，不是没实现。

**A. 侧边栏翻页：手势区从 34dp 的圆点条扩到整条面板头**

- 原实现把竖滑重手势只绑在三个圆点那一条（34dp 高），阈值还是**屏高的 38%**
  （≈290dp）+ 速度 1200dp/s——技术上能翻，但要先精准戳中那条窄条、再拖将近三分
  之一屏，手感上等于翻不动。文档 §6.0 写的是"面板头部/空白区提供翻页"。
- 现在手势区 = **面板头整条**（页名行 + 圆点行），阈值改为绝对行程 90dp / 速度
  800dp/s；列表区仍然只滚动、不翻页，"重手势防误翻"的初衷保住。
- 圆点同时是**跳转靶**：点哪个跳哪页（原先只能点左右半区 ±1，没有任何 affordance）。
- **明确不做横滑翻页**：面板那一层的横滑是 §6.5 隐私过头用的，让 `PageView` 接管
  横方向会把它吃掉。

**B. 疑问笔记路径：补上系统文件选择器**

- 原设置项只有一个手输 `TextField`；同一页的任务目录却有『用系统选择器挑一个目录』。
  §6.2 空态文案写的是"去设置**选择文件**"——选择器本来就该有。
- `FolderPickerPort` 加 `pickFile()`（该端口注释本就是"目录/文件选择"），安卓与桌面
  适配器都走 `FilePicker`；设置项改成与任务目录同款的底部弹层（输入框 + 选择器 +
  保存），**手输保留作兜底**。桌面口径：**文件可挑，目录仍不挑**（目录走环境变量
  / 引导配置这条原口径不变）。

**C. 拖动排序不再闪动：整段重编号改批量落盘**

- 现象：拖完条目在几个位置之间上下跳，最后才停。根因不是动画，是**一次手势被做成
  N 次"逐条写盘 + 逐条发事件 + 逐条重锚"**——第 k 条写完时只有前 k 个序号是新的，
  那个半成品顺序立刻被 `buildPoolView` / `buildTodayView` 渲染出来。
- 修法：新增 `setPoolOrders(taskIds)` 与 `setPinnedStack(taskIds)`，照既有
  `setManualOrder` 的形状——批量落盘 → 内存态整体换成终态 → **一个事件** → **一次重锚**。
  无排序档本来就是这么写的，所以那一档从不闪，这次把另外两档对齐。
- 附带修掉一条：`_onReorder` 的 `insert >= oldPinnedCount` 在插队区为空时恒真，
  **标准/完整档下第一次拖动永远是空操作**——插队区根本没有入口。改为拖到最顶即插队。
- `setPinnedStack` 的插队时刻按目标顺序递减 1 毫秒写：同一毫秒并列会让按字符串排序
  失去稳定依据，落位变随机（表现为"闪完停在别处"）。

**D. 验证状态 = 未验证（工具链 231 故障）**

`dart analyze` / `flutter analyze` 本次连试 8 次全部撞 Windows 命名管道耗尽
（OS error 231），与改动无关（v0.12 起就是这一状态）。真机四项必测：① 面板头部上下
拖能翻页、点圆点能跳页、列表区拖动不会误翻；② 设置里挑笔记文件能弹出系统选择器、
挑完路径入框且疑问页立刻读到内容；③ 池子拖一段、今日拖一件，落位一次到位不再闪；
④ 标准档下把一件拖到最顶能插队（原来做不到）。

### v0.15（2026-10-13）：翻页改左右横滑，隐私过头改显式入口

两道手势一起删：用户明确"我的想法并不是这么实现的"。需求口径的变化 = 决议 45。

**A. 翻页：垂直重手势 → 左右横滑**

- 原口径是"三页**垂直**翻页 + 重手势（更大行程/速度阈值）"。这条从一开始就是拧的：
  纵向是**列表滚动**的地盘，翻页要借用同一个方向，就只能在"拖不够翻不动"和
  "拖一点就误翻"之间二选一——实现先绑在 34dp 的圆点条上、后又扩到面板头整条，
  都是在给这个错的方向打补丁（v0.14 那一轮就是补丁）。
- 现在三页**左右横滑**翻页（`PageView` 默认物理）：横滑与列表的纵向滚动方向正交，
  天然不冲突，也就不需要"重手势"这个补偿机制。圆点保留，仍是可点的跳转靶。
  （**v0.14 那条"明确不做横滑翻页"随本条作废**——它成立的前提是"横滑归隐私过头"，
  那道手势现在没了。）
- **边缘那一小条仍归系统返回**（沿用决议 41：面板那层不声明手势排除区），所以翻页
  从面板内部起手——这条写进 §6.0，免得将来被当成"边缘横滑翻不动"的 bug。

**B. 隐私过头：删掉"拖拽过头"那道横滑**

- 横滑归翻页后它没有立足之地；更根本的是"拖过头"没有 affordance——不拖到那一步
  根本不知道有这个功能，误拖进去又是一片空白，比没有更糟。
- 入口改为**面板头『隐私』按钮**（应用内面板与悬浮面板同一处，这个按钮本来就在），
  退出走系统返回 / 收起面板，不再是"再拖一次才回来"。
- **功能本身保留**：§6.5 的"只留一条输入框"与决议 22 的"等价堆三无"一条不变。

**C. 连带同步的小节**

§0 原则 3、§6.0、§6.5、§6.6 引导三步、§11 误触防护、决议 45（新增），
architecture.md §5.1 安卓壳描述，crosswalk 第 11 行与旧词表 3 行。

**D. 代码已落地；`dart analyze` 通过，真机未验证**

落点：`side_panel.dart`（去 `NeverScrollableScrollPhysics`、删竖滑回调与面板头手势区、
圆点保留为跳转靶、引导第二步改文案）、`android_shell.dart`（删包在面板外的
`onHorizontalDragEnd`、删两个阈值常量与 `_pageBy`）、`overlay_main.dart`（同样删阈值与
回调）。`dart analyze lib` 通过（4 条既有 info：`onReorder` 已废弃、`_modeButton` 的函数
声明风格）；`flutter test` 仍因本机命名管道故障（`WebSocketException: Invalid WebSocket
upgrade request`）跑不起来，与改动无关。真机四项必测：① 页面区左右横拖能翻页、上下拖
仍是滚清单；② 点圆点能跳页；③ 面板头眼睛按钮进隐私、返回键退出（不再是"再拖一次"）；
④ 从屏幕最边缘起手横拖仍可能被系统返回吃掉——这是决议 41 的取舍，不是 bug。
