# 文档规则与索引

这份文件是**动手改文档之前**看的：先查这件事该落哪一份，再照规则写。
只想找内容的人跳过"写作与改动规则"那节，直接查上面两张表。

三份东西分工不同，别混：

- 仓库根的 `README.md`：这是什么、和普通待办的区别、怎么装（面向使用者）。
- 仓库根的 `AGENTS.md`：怎么跑、怎么打包、代码怎么分层、两个会踩的约定（面向改代码的人）。
- **本页**：文档放哪、怎么写、改哪一份。
- `architecture.md` / `ui-interaction.md`：正文。

一句话原则：**一份事实只有一个家**。定义只写在拥有它的那份里，别处一律改成链接。

## 写作与改动规则

1. **先改文档再改代码**。结构、接口、数据格式、交互的变更，先在对应文档里落定，
   再动实现——提交也按这个顺序拆笔，方便回滚。
2. **一份事实一个家**。发现同一句话在两处出现，改第二处为链接，不要两处一起维护。
3. **只写现状**。正文不写"已实现 / 计划中 / 这次改成了"：状态由代码和测试承载，
   历史归 commit，理由归 `decisions/`。真有边界要登记，写进 `architecture.md` §11 或
   `ui-interaction.md` §11 的表格里。想写计划，去 `roadmap.md`。

   两种"历史"处理相反，别混：**被撤销的旧口径**就地划掉（`~~…~~`）并在旁边一句写清
   为什么撤——读者需要知道"这条路走过、不通"；**进度与完成账本**（版本 changelog、
   "已完成 ✅"清单）一律不留，它只是工作日志，commit 里有。

4. **引用怎么写**。`§3.1` 这类编号**不带文件名时只在本文档内用**。跨文件二选一：

   - **路径链接**（正文首选）——四个方向：`docs/` 根 → 子目录
     `[formats/sidecar.md](formats/sidecar.md)`；子目录 → 同目录 `[今日清单页](today.md)`；
     子目录 → 正文 `[UI 文档](../ui-interaction.md) §9 第 12 条`；
     子目录 → 另一子目录 `[formats/mainline.md](../formats/mainline.md)`。
   - **全文件名 + §**（查表、一句里要指好几节时用）：`` `architecture.md` §3.1 ``。
     本文件上面两张表就是这种写法。

   **不能只写 `§3.5`，也不能写别名**（`架构合同 §6`、`arch §5.1`）——两种都会被当成
   本文档的章节，指错了也查不出来（门禁对紧贴 `§` 的别名直接警告）。编号还会随文档
   拆分搬家，路径链接至少点得进去、错了看得出来。

5. **什么时候写决策卡片**：见 [`decisions/README.md`](decisions/README.md)。
   一句话判据——这个取舍半年后可能被重新提出来。

6. **文档坏了 `flutter test` 会红**。`test/docs_test.dart` 扫全部文档，查七件事：
   死链、自指链接（`[主线文件](mainline.md)` 写在 mainline.md 里，点进去还是这一页）、
   章节引用指不到东西（含 `§4.2 的边界表` 这种指向已搬空的索引节）、
   代码块里的链接（渲染成字面文本、点不了）、正文出现状态词
   （"这次改成 / 已实现 / 【规划】/ ✅"）、正文出现版本号
   （`v1.27` 这类——版本号本来是坐标，可它指向的 changelog 与决议表都不在文档里，
   读者拿着它无处可查；写进反引号当示例不算）、以及 `§` 前面紧贴文档别名
   （`架构合同 §6` 会被当成本文档，指错也查不出来——写路径链接）。
   不用记命令——跑测试就顺带查了。

   想只看文档（比全量测试快）：`dart run tool/check_docs.dart`，加 `--strict`
   时警告也算失败。

   改检查规则本身（`tool/doc_lint.dart`）时跑 `test/doc_lint_test.dart`——门禁
   自己也得被测，否则它只是"看起来在检查"。写新规则时先写反例（断言它会红），
   不然没法证明它不是永远绿。
