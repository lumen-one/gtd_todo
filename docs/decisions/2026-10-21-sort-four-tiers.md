# 决定：排序按四种展示状态分池

记录：2026-10-21
状态：生效中

## 问题

调度结果是一张按调度优先级排好的列表，但"排得靠前"有两种完全不同的原因：任务真的急
（裕度薄），和任务已经确定做不到（裕度是负的）。

按一个连续的分数排，这两类会混在同一个池子里。后果是：一个重要度 5、但裕度还宽的
任务，会压住一个重要度 1、但已经确定做不完的任务——而后者才是唯一需要现在就决策的
那件（改期、放弃、还是加急）。

## 决定

`TaskDisplayStatus` 分四档，排序时先分档、档内再按调度优先级排：

```dart
enum TaskDisplayStatus { normal, infeasible, overdue, snoozed }
```

`overdue` 是派生事实，不落盘——由当前时间与截止期算出来，写进文件只会产生需要同步的
脏数据。`infeasible` 同理，它是"剩余工时 > 可用工时"的判定结果，不是人设的状态。

## 备选与为什么输

**一个池子，只按 `priority = risk × importance` 排。**
输在：`risk = f(slack)` 是非线性的，裕度转负之后它的绝对值能吃掉好几倍的重要度差。
结果是"已经做不到的事"被埋到列表下半部分——恰好把最需要处理的那类藏了起来。分档
不是为了让排序更准，是为了让"做不到"这个状态不被数值淹没。

**只把逾期任务永远置顶。**
输在：逾期和不可行是两件事。前者已经过了截止，后者是算出来做不完、但还没到截止。
只置顶逾期，那些"明天到期但还差 20 小时工时"的任务仍然会被压住。

## 代价

- **四档是硬边界**：任务从"不可行"变回"可行"时会跳档，排序结果不连续。使用者看到的
  是"位置突然变了"，而不是"慢慢往上浮"。
- **档内仍要排序**：分档只把最需要解释的那一类单独拎出来，没有消除"为什么它在我前面"
  这个解释成本——同一档里还是要靠一个分数说话。
- **每加一个展示态都要多铺一遍**：今日页的分组、条目徽标、长按菜单的可用动作，都要
  分别想清楚它落在哪。这是持续的维护成本，加状态前先确认它真的配得上单独一档。
